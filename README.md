# Wind & Rain Route Overlay

Планировщик велосипедных маршрутов по погоде: загружаешь GPX, приложение считает
встречный/попутный ветер и осадки **в тот момент, когда ты реально будешь в этой точке**,
и подсказывает лучшее время старта на ближайшие 48 часов.

## Структура

| Папка | Что это |
| --- | --- |
| `shared/` | Вся логика погоды и маршрута: чистый TypeScript без DOM и без React |
| `mobile/` | Приложение на Expo — экран радара с маршрутом |
| `src/` | Веб-версия на Vite: слайдер времени старта, окна дождя, профиль высоты |

`shared/` подключается по алиасу `@shared/*` — в вебе через `vite.config.ts`,
в мобильном через `metro.config.js` (`watchFolders` + `extraNodeModules`).
Правка расчётов сразу видна в обоих приложениях.

### Мобильное приложение

```bash
cd mobile
npm install
npx expo run:ios      # или run:android
```

Expo Go не подойдёт — нужна нативная сборка: карта на MapLibre GL
(`@maplibre/maplibre-react-native`), это нативная зависимость.

Подложка своя (`src/lib/mapStyle.ts`), а не готовый стиль: дороги, здания и POI под
облачностью и радаром — шум, в котором ничего не разобрать. Остались плоская суша,
вода, границы и подписи городов; векторные тайлы берутся у OpenFreeMap (бесплатно,
без ключа). Погодные растры вставляются слоями-якорями между водой и границами,
поэтому названия городов читаются даже под сплошной облачностью — так же устроены
подложки погодных приложений.

Внизу — таймлайн с play: карта показывает погоду на выбранный момент, оранжевый
маркер — где велосипедист будет в это время. Шкала начинается с начала радарной
истории (до 2 часов назад), чтобы было видно, идёт облако на маршрут или уходит.

Кадры облачности не переключаются встык, а перекрываются: новый монтируется вторым
слоем, получает фору на загрузку тайлов и проявляется поверх старого через
`raster-opacity`. Пока он проявляется, старый лежит под ним непрозрачным — поэтому
при перемотке и проигрывании карта не мигает.

### Веб-версия

```bash
npm install
npm run dev
```

## Откуда берутся данные о погоде

Два принципиально разных источника — ровно как в мобильных приложениях-радарах.

### 1. Радар осадков — наблюдение (RainViewer)

`shared/radar.ts`

Метеорадар — это не прогноз, а измерение: импульс отражается от капель, по силе
эха (dBZ) считается интенсивность осадков. Национальные сети радаров публикуют
композитные мозаики каждые 5–10 минут:

| Регион | Сеть |
| --- | --- |
| США | NEXRAD / NOAA MRMS |
| Германия | DWD RADOLAN |
| Великобритания | Met Office |
| Канада | Environment Canada |
| Франция | Météo-France ARAMIS |
| Япония | JMA |

[RainViewer](https://www.rainviewer.com/api.html) сшивает их в один глобальный слой и
отдаёт XYZ-тайлы. Индекс кадров — `https://api.rainviewer.com/public/weather-maps.json`:

* `radar.past` — примерно 2 часа наблюдений, шаг 10 минут;
* `radar.nowcast` — до ~30 минут вперёд, экстраполяция движения засветки
  (наукаст, не модель);
* тайл: `{host}{path}/{size}/{z}/{x}/{y}/{color}/{smooth}_{snow}.png`.

Ограничения бесплатного (безключевого) доступа, заложенные в код:

* тайлы отдаются только до **z=7** — выше сервер возвращает картинку
  «Zoom Level Not Supported». Поэтому слой запрашивает тайлы 512px и
  ограничен `maxNativeZoom`, а на крупных масштабах Leaflet растягивает
  последний доступный уровень (детализация ~1 км/пиксель);
* индекс публикуется с задержкой, поэтому последний скан считается
  актуальным ещё один интервал (`LAST_FRAME_GRACE_MS`);
* лимит 500 запросов в минуту.

### 2. Прогноз модели — за пределами радара (Open-Meteo)

`shared/wind.ts`

Радар не умеет заглядывать дальше получаса. Для планирования на 48 часов берётся
почасовой прогноз численных моделей через
[Open-Meteo](https://open-meteo.com/) (без ключа): ICON, GFS, а в Европе —
локальные модели высокого разрешения. Запрашиваются `windspeed_10m`,
`winddirection_10m`, `precipitation`, `precipitation_probability` сразу для 12 точек
вдоль маршрута одним запросом (Open-Meteo принимает координаты через запятую).

Запрос идёт с `timezone=GMT`, и к каждой метке времени дописывается `Z`. Иначе
`new Date("2026-09-07T18:00")` прочитал бы время маршрута как время устройства —
и для маршрута в чужом часовом поясе весь расчёт съехал бы на несколько часов.

Приложение честно показывает, какой источник сейчас на карте: плашка
**«радар · наблюдение»** или **«модель · прогноз»** в блоке проигрывания.

### 3. Облачность — снимок на прошлое, модель на будущее

`shared/satellite.ts`, `shared/clouds.ts`

Настоящие тучи с рваными краями, а не размытые пятна, — это снимок геостационарного
спутника. Над Европой его даёт Meteosat: EUMETSAT публикует композит MTG GeoColour
открытым WMS-сервисом `view.eumetsat.int` без ключа — дневной натуральный цвет и
ночная ИК-подсветка облаков в одном слое, шаг 10 минут, разрешение над Европой ~2 км.
Родного разрешения хватает примерно до зума 8, выше карта просто растягивает те же
пиксели, поэтому потолок зума ограничен.

Снимок знает только то, что уже было, а маршрут планируется вперёд. Поэтому дальше
последнего кадра облачность рисует модель Open-Meteo: сетка 16×16 точек по границам
маршрута, поле интерполируется в одну картинку и кладётся на карту через
`<ImageSource>`. Тон картинки подогнан под снимок, чтобы стык не бросался в глаза.

Ровно та же схема — наблюдение на прошлое, прогноз на будущее — используется в
погодных приложениях: у Weather&Radar это слои `satlayerObs` и `satlayerProg`.

## Что считается

### Скорость — из физики, а не из средней по больнице

`shared/physics.ts`

Мощность = качение + аэродинамика + уклон. Обратная задача (по целевой мощности
найти скорость) — кубическая, решается делением пополам. Плотность воздуха берётся
из температуры и давления: разница между −5 °C и +30 °C — около 13% сопротивления.

Это не украшение: `shared/scoring.ts` идёт по сегментам **последовательно**,
потому что скорость на сегменте зависит от ветра в момент прибытия, а момент
прибытия — от скорости на предыдущих. Плоская средняя скорость врала бы на
десятки минут, и в точку маршрута подставлялся бы прогноз не на тот час.

Отсюда же «цена ветра»: та же поездка при той же мощности в безветрие — и разница
в минутах. На замкнутой петле она всегда положительна (встречный отнимает больше,
чем попутный отдаёт).

### Проскочить между дождями

`shared/dodge.ts`

Сетка «задержка старта × целевая мощность»: для каждой пары считается, сколько
километров придётся ехать под дождём. Ответ вида «выехать на 105 мин позже и
держать пониже темп — проедешь сухим; если ждать нельзя, +45 мин и повыше темп —
под дождём 3.9 км».

Сетка принципиально не монотонна: иногда ехать **медленнее** выгоднее, потому что
ячейка успевает уйти вперёд. Обычные приложения этого не видят — они показывают
погоду в точке, а не вдоль движения.

Осадки для этого берутся с шагом 15 минут (`minutely_15`), иначе сдвиг старта на
15 и на 45 минут давал бы одинаковый ответ. Геометрия маршрута считается один раз
на всю сетку, а выборка из рядов прогноза — арифметикой по индексу, а не
перебором: 45 вариантов на маршрут в 119 сегментов считаются за ~15 мс.

### Остальное

* `weatherCost` — сводная «цена» погоды в минутах: потерянное на ветер время +
  штраф за долю маршрута под дождём + штраф за интенсивность. По ней выбирается
  лучшее время старта.
* `RainWindow` — непрерывные участки «с какого по какой километр и в какие минуты
  ты едешь под дождём».

## Интерфейс веб-версии

* **Слайдер времени старта** — 48 часов вперёд, шаг 1 час, плюс вариант «сейчас».
* **Проигрывание поездки** — карта показывает погоду на выбранный момент, оранжевый
  маркер — где ты будешь в это время. Шкала начинается с начала радарной истории
  (до 2 часов назад), чтобы было видно, приближается облако к маршруту или уходит.
* **Карта** — заливка трека по встречному/попутному ветру, стрелки ветра, слой
  радара с регулировкой прозрачности; вне покрытия радара осадки рисуются кругами
  по модельному прогнозу.
* **Дождь по маршруту** — полоса дистанции с мокрыми участками и список окон дождя.
